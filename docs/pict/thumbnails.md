# Номер изображения в имени превью

## Назначение

`pict/thumbnails.py` содержит `CatalogThumbnailBackend`, наследник штатного `sorl.thumbnail.base.ThumbnailBackend`. Он подключён единой настройкой `THUMBNAIL_BACKEND`, восстанавливает удалённые файлы превью при устаревших метаданных и добавляет `Pict.name` перед расширением производного файла: `cache/thumbnails/89/52/89525d6de4493a0eae5045afd7723a78-275.jpg`. Это номер изображения в каталоге, а не первичный ключ записи.

## Формирование имени

- При передаче `Pict.photo` backend берёт номер из экземпляра модели, которому принадлежит `ImageFieldFile`. Правило действует для сетки каталога, избранного, похожих изображений, связанных превью в готовых работах, крупного модального превью, индивидуальной страницы и admin.
- Номер передаётся опцией `catalog_image_number`, которая удаляется до штатного вычисления хеша и обработки изображения. Поэтому хеш, вложенные каталоги, геометрия, качество и расширение остаются прежними; меняется только суффикс имени. Значение преобразуется в целое число, поэтому через опцию нельзя добавить произвольный путь.
- Номер не извлекается из имени оригинала: исторические файлы, storage-суффиксы и произвольные названия не мешают идентификации. После изменения `Pict.name` следующее обращение получает превью с текущим номером, даже если оригинал не переименован.
- Для фотографий готовых работ, статей, квиза и других моделей сохраняется штатное имя. Строка пути не содержит связи с записью и без явной опции тоже обрабатывается штатно. Код, которому нужно нумерованное превью каталога, должен передавать `picture.photo`; для строкового пути можно явно передать `catalog_image_number`.
- Явная опция имеет приоритет над текущим полем экземпляра. `AdminImagePreviewMixin.get_object()` запоминает `_admin_saved_image_number` вместе с прежним фото и передаёт этот номер при построении admin-превью. Если валидация изменила номер в объекте формы, но сохранение не состоялось, превью остаётся прежним и лишний файл не создаётся. Снимок принадлежит только загруженному объекту и не хранится в общем `ModelAdmin`.
- Отдельного поиска записи по пути нет. В `pict_large_preview` поля `photo` и `name` выбираются одним запросом, чтобы обращение к отложенному полю номера не добавляло SQL.

## Переход со старого кеша

Миграция схемы, переименование оригиналов и массовое обновление ссылок не нужны. При первом запросе нужного размера `sorl-thumbnail` создаёт нумерованный файл и сохраняет его в существующем KV-хранилище; повторный запрос использует этот файл без декодирования оригинала. Прежние файлы без номера остаются доступны по старым URL. Новые варианты создаются по мере просмотра, без предварительного обхода всего каталога; до очистки старых копий объём кеша увеличивается.

Старые и новые превью зарегистрированы у одного источника. Существующая [очистка фотографий](photo-cleanup.md) при замене или удалении неиспользуемого оригинала удаляет обе версии и их KV-записи после commit. Смена номера сама по себе прежний кеш не удаляет. Эта доработка не запускает массовую очистку и не меняет рабочую БД или media при установке кода.

## Восстановление после очистки

Команда `python manage.py thumbnail clear_delete_all` удаляет файлы под `THUMBNAIL_PREFIX` и KV-записи в БД. При `LocMemCache` у каждого процесса своя память: запуск команды в консоли не очищает локальные записи уже работающего web-процесса. Штатный backend возвращает найденные метаданные без проверки файла; поэтому ранее просмотренная миниатюра могла остаться пустой, а ещё не запрошенное крупное превью создавалось нормально.

`CatalogThumbnailBackend.get_thumbnail()` проверяет наличие возвращённого файла в storage. Если файла нет, но метаданные остались, он удаляет только KV-записи этого превью и его источника с `delete_thumbnails=False`, затем один раз повторяет штатное создание. Запись источника обновляется также в БД, чтобы восстановленный кеш был доступен другим процессам. Файл оригинала и остальные размеры не удаляются; их связь с источником сохраняется. Это действует и для ненумерованных превью других моделей.

При обычном попадании в кеш добавляется только проверка наличия файла; дополнительных SQL-запросов и повторного декодирования изображения нет. Если первичное создание не удалось и метаданные не записаны, backend не повторяет попытку: сохраняется штатная обработка ошибок и резервный вывод оригинала. Восстановление удалённого кеша происходит при следующем обращении без перезапуска сервера.

## Проверки

`pict/test_thumbnails.py` создаёт JPEG во временном `MEDIA_ROOT` и проверяет:

- переход с существующего кеша для размеров 760/1920 и формата PNG, сохранение хеша и оригинала;
- повторное использование кеша без декодирования и SQL;
- исторический путь с чужим номером и storage-суффиксом, последующую смену номера;
- прежние имена превью готовых работ и строковых путей;
- приоритет явного номера, номер `0` и отклонение произвольного пути вместо номера;
- удаление оригинала, обеих версий превью и KV-записей после commit;
- нумерованные URL в каталоге, избранном, индивидуальной странице и готовых работах;
- крупное превью с единственным SQL-запросом за изображением;
- реальный `thumbnail clear_delete_all` с отдельным `LocMemCache`, имитирующим процесс команды: восстановление миниатюры каталога, KV-записей источника и превью, последующую очистку из другого worker;
- восстановление удалённого файла для каталога и готовых работ без удаления других размеров;
- отсутствие повторного создания при ошибке чтения оригинала.

python manage.py test pict.test_thumbnails pict.tests.CatalogThumbnailTests pict.tests.AdminImagePreviewValidationTests pict.test_photo_cleanup
