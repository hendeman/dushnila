# Доставка контактных заявок

## Состав

`pict/services/contact_delivery.py` управляет общей SQLite-очередью. Реестр `ADAPTERS` связывает `telegram` с `telegram_delivery.py`, `email` с `email_delivery.py`. Каждый адаптер предоставляет проверку конфигурации и отправку одной доставки. Общие безопасные исключения находятся в `delivery_errors.py`, формат сообщения — в `delivery_messages.py`.

Подключения, правила маршрутизации и зашифрованные настройки принадлежат `sitecontent.LeadConnection`; см. [Обработка заявок](../sitecontent/lead-processing.md). Добавление нового сервиса требует его формы/валидации и адаптера; публичные формы и алгоритм повторов используют общий механизм.

## Постановка в очередь

`enqueue_contact_request()` выбирает включённые подключения, проверяет тип заявки и создаёт недостающие доставки каждому получателю. `get_or_create()` и уникальность тройки заявки/подключения/адреса предотвращают повторную постановку. Адрес сохраняется в записи доставки. Существующая историческая строка без адреса предотвращает повторную постановку заявки в то же подключение при любом источнике настроек. Функция атомарна и вызывается внутри транзакций публичных обработчиков, включая сохранение снимка квиза. При отсутствии подключений заявка сохраняется без доставок.

`enqueue_connection_test()` проверяет локальную конфигурацию и создаёт группу доставок с общим `test_batch_id` без `ContactRequest`. Сообщение содержит только стандартный тестовый текст. Тесты проходят через ту же команду, даже если подключение выключено; веб-запрос не выполняет внешнюю отправку.

## Обработка очереди

`process_pending_deliveries()`:

1. Проверяет положительные параметры и восстанавливает `processing`, зависшие дольше 10 минут. При исчерпании попыток ставит `failed`.
2. Находит подключения с готовой очередью, расшифровывает и проверяет их конфигурацию. Ошибка сохраняется в `LeadConnection.configuration_error`, очередь этого подключения не захватывается и не расходует попытки; другие подключения продолжают обработку.
3. Выбирает до 20 готовых `pending`/`retry` среди корректно настроенных подключений. Обычные доставки выключенных подключений пропускаются.
4. `claim_delivery()` условным атомарным UPDATE закрепляет запись за процессом, увеличивает попытки и ставит `processing`. Повторное чтение загружает подключение, заявку и снимок квиза через `select_related()`.
5. Выполняет внешний запрос после завершения записи в БД, без открытой транзакции.
6. Сохраняет `sent`, время и строковый внешний ID либо назначает повтор через 1, 5, 15 и затем 60 минут. Telegram `retry_after` имеет приоритет.
7. После пяти попыток либо постоянной ошибки ставит `failed`.

Фиксация результата проверяет статус, время захвата и номер попытки: поздний ответ старого процесса не перезаписывает результат новой попытки после восстановления. Короткие транзакции подходят для текущей нагрузки SQLite. `retry_failed_deliveries()` переиспользуется обеими admin-страницами и возвращает только `retry`/`failed`, обнуляя число попыток.

## Telegram

Адаптер читает токен и прокси из зашифрованных полей или, для подключения с `use_environment=True`, прежние `TELEGRAM_*`. Прокси допускается только HTTP(S) с хостом и явным портом. Отдельная `requests.Session` имеет `trust_env=False`; системные HTTP_PROXY/HTTPS_PROXY/NO_PROXY не влияют на запрос. При заданном прокси прямого обхода нет. Тайм-ауты connect/read раздельные.

`sendMessage` вызывается с `parse_mode=HTML`. Успех подтверждается `ok=true` и целочисленным `message_id`; HTTP 200 сам по себе недостаточен. ID сохраняется как строка. 429, 5xx, тайм-ауты и сетевые ошибки назначают повтор; явные постоянные ошибки завершают доставку. Сохраняется безопасное сообщение с кодом ошибки, без исходного описания API или текста сетевого исключения: они могут содержать секреты либо данные клиента.

Общий формат содержит иконку и номер заявки, выделенный тип, имя, заполненные контакты, вопрос/комментарий, номер изображения, ответы квиза и время. Пользовательские значения HTML-экранируются. Функция `format_contact_request_message()` импортируется также через `contact_delivery.py` для существующих потребителей.

## Email

Адаптер использует штатный Django `EmailBackend` с параметрами конкретного подключения, обязательным STARTTLS или SSL/TLS и ограниченным тайм-аутом. Перед подключением он дополняет системное хранилище доверенных корневых сертификатов набором `certifi`; проверка цепочки сертификата и имени SMTP-сервера остаётся обязательной. Это устраняет ошибку подтверждения сертификата SMTP-сервера на системе с неполным набором доверенных корней без отключения TLS-проверки. Каждая доставка содержит единственного получателя; временный отказ одного адреса не повторяет успешные отправки остальным. Письмо содержит текстовую и HTML-версию общего сообщения, контактный email клиента попадает в `Reply-To`. Отправитель берётся из настроек подключения. Стабильный заголовок письма `Message-ID` строится локально из UUID доставки и домена отправителя и сохраняется при повторах. Он записывается в общее поле `external_message_id`, хотя SMTP-сервер не возвращает этот идентификатор; его наличие подтверждает только успешное принятие сообщения SMTP-сервером, а не доставку во входящие.

SMTP 4xx и сетевые сбои считаются временными; 5xx, ошибки TLS и неподдерживаемое защищённое соединение — постоянными. Исходные ответы сервера и исключения не записываются. Подтверждение SMTP означает принятие письма сервером, без гарантии получения/прочтения адресатом. Взаимодействие выполняется через [Django EmailBackend](https://docs.djangoproject.com/en/5.2/topics/email/).

## Гарантии и ограничения

- Сбой внешнего сервиса не удаляет сохранённую заявку.
- Доставка выполняется как минимум один раз: при принятом сообщении и потерянном ответе повтор может создать дубликат. Ни Telegram, ни обычный SMTP не дают здесь гарантии «ровно один раз».
- Новые и уже поставленные доставки учитывают выключение подключения. Уже начатый сетевой запрос может завершиться после выключения.
- Изменение получателей применяется к новым доставкам; накопленные сохраняют адрес. У исторических Telegram-записей адрес отсутствовал: используется прежний TELEGRAM_CHAT_ID либо единственный явно заданный Telegram-получатель, в том числе после смены источника секретов. Неопределённый адрес оставляет старую строку в очереди без расхода попыток; доставки с известными адресами продолжаются.
- Тесты имеют отдельные записи без заявки и не появляются в списке заявок клиентов.
- Новые подключения получают только новые заявки; прежние можно явно поставить через действие списка заявок.
