# Миграции приложений проекта

## Назначение

Сводка Python-файлов в `skinali/pict/migrations/` и `skinali/sitecontent/migrations/`. Миграции `pict` образуют цепочку от `0001` до `0036`; `0025` также зависит от модели пользователя, а `0028` — от `sitecontent/0003`. У отдельного приложения управляемого содержимого своя цепочка из трёх миграций. Оба `__init__.py` пусты и только обозначают пакеты.

Текущую итоговую схему удобнее смотреть в [models.md](../pict/models.md). Этот документ нужен для истории изменения БД и выбора миграции при диагностике.

## Итог после `0036`

- `Category`, `Color`, `TagPict` — отдельные справочники с уникальными slug; `Category` дополнительно хранит индексированную управляемую позицию и сортируется по ней, `Category` и `TagPict` хранят необязательные управляемые `seo_h1`, `seo_title`, `seo_description`, `intro_text`, а `TagPict.normalized_tag` — уникальное нормализованное поисковое значение.
- `TagAlias` каскадно принадлежит одному `TagPict` и хранит исходный синоним вместе с уникальным `normalized_alias`.
- `Pict.name` — уникальный индексированный целочисленный номер изображения; в Django Admin поле подписано «Номер изображения». `Pict.slug` уникально адресует индивидуальную страницу и после создания не меняется автоматически.
- `Pict.alt` обязателен в штатной валидации Django; новые `Pict.photo` сохраняются под транслитерированным именем из описания с добавленным значением `Pict.name`. Цифры исходного имени файла не используются.
- `Pict.page_description`, `seo_h1`, `seo_title` и `seo_description` допускают пустое значение, при котором публичная страница использует автоматический уникальный текст с номером изображения.
- `Pict.created_at` сохраняет прежнее время добавления, а `Pict.updated_at` отслеживает последующее изменение.
- Категории, цвета и теги связаны с изображениями many-to-many.
- `Pict.title` отсутствует.
- Модель сохраняет стандартную сортировку по убыванию `id`; публичный каталог, категории и цветовые фильтры явно сортируют сначала по `-is_popular`, затем по `-id`.
- `Pict.is_published` по умолчанию равен `True`; публичные выборки каталога используют только опубликованные записи.
- `Pict.is_popular` по умолчанию равен `False`; отмеченные записи выводятся перед обычными в публичном каталоге, категориях и цветовых фильтрах.
- `FinishedWork` хранит одну фотографию готовой работы, фиксированные типы стекла и скинали, необязательный цвет покраски и при необходимости ссылается на одно изображение каталога; новый или заменённый файл фотографии получает транслитерированное имя из `FinishedWork.name`, обратная связь — `Pict.finished_works`.
- Типы не создают справочных таблиц: сохранены кодами `TextChoices` в строке готовой работы. Ограничение БД требует цвет только для покраски и запрещает номер изображения для покраски и прозрачного скинали.
- Удаление связанного `Pict` не удаляет готовую работу, а обнуляет `catalog_image`.
- Готовые работы сортируются по убыванию времени создания и ID; независимый `FinishedWork.is_published` по умолчанию равен `True` и управляет публичным показом, а `updated_at` фиксирует изменения.
- `ContactRequest` хранит валидные заявки пяти типов: телефонные формы используют телефон и вопрос, обычная email-форма — настоящий email и комментарий, заявка покупки дополнительно хранит проверенную связь с `Pict` и снимок номера изображения, а заявка квиза связана со снимком вопросов и ответов в `QuizSubmission`. После удаления `Pict` снимок номера сохраняется. `viewed_at` фиксирует первый просмотр в admin; новые и исторические непросмотренные заявки имеют `NULL`. Записи сортируются от новых к старым.
- `ContactRequestDelivery` независимо отслеживает Telegram/email-каналы и каскадно принадлежит одной заявке; сейчас новые формы создают Telegram-доставку `pending`.

## Правила для ИИ-агента

- Не редактировать примененные исторические миграции для обычного изменения схемы; менять модель и создавать новую миграцию.
- Перед изменением схемы проверить [models.md](../pict/models.md), фактический `models.py` и состояние миграций через `python manage.py showmigrations pict`.
- После создания миграции добавить ее в эту таблицу и обновить итоговую схему при необходимости.
- При проблеме перехода между конкретными версиями открыть соответствующий исходный файл миграции: сводка не содержит всех сериализованных параметров полей.

## `0025_integrations`

Создаёт `Integration` для HTML/JS-вставок сайта и `IntegrationRevision` для истории снимков. Зависит от `0024_contactrequest_viewed_at` и заменяемой модели пользователя (`AUTH_USER_MODEL`). Новые интеграции по умолчанию выключены; миграция не создаёт записей и не изменяет существующие данные каталога. См. [интеграции](../pict/integrations.md).

## `0026_tag_search_terms`

Зависит от `0025_integrations` и выполняется в безопасной последовательности:

1. добавляет в `TagPict` временно nullable-поле `normalized_tag` без уникальности;
2. нормализует все существующие теги по тем же правилам NFKC, `casefold()`, `ё` → `е` и поисковых разделителей;
3. записывает значения через `bulk_update()` пачками до 500 строк;
4. делает поле обязательным и уникальным;
5. создает `TagAlias` с внешним ключом на основной тег, исходным `alias` и уникальным `normalized_alias`.

Data-миграция не пытается автоматически объединять данные. Она прерывается с `RuntimeError`, если нормализованное значение не содержит ни одной буквы или цифры, длиннее 200 символов или совпадает у двух существующих тегов. Перед повторным применением конфликтующие исходные теги нужно исправить вручную. Обратная функция для заполнения значений — `RunPython.noop`; откат схемы удаляет созданные поле и таблицу обычными обратными операциями миграции. Синонимы миграция не создает.

Уникальность каждого нормализованного поля обеспечивается внутри его таблицы. Запрет совпадения значения между `TagPict.normalized_tag` и `TagAlias.normalized_alias` реализован валидацией текущих моделей, а не межтабличным ограничением этой миграции. Правила поиска описаны в [search.md](../pict/search.md).

## `0027_taxonomy_seo_content`

Зависит от `0026_tag_search_terms` и добавляет одинаковые четыре поля непосредственно в таблицы `Category` и `TagPict`: `seo_h1` и `seo_title` длиной до 200 символов, `seo_description` длиной до 320 символов и неограниченный `intro_text`. Все поля допускают пустую строку, поэтому миграция не требует заполнения существующих записей и не меняет их публичное отображение: представления продолжают использовать стандартные значения до ручного заполнения полей в Django Admin.

Абстрактный Python-класс `SeoLandingContent` не создаёт отдельной таблицы и не добавляет связей между моделями.

## `0028_public_content_timestamps`

Зависит от `pict/0027` и `sitecontent/0003`. Прежнее поле `Pict.time_update` переименовывается в `created_at` без потери сохранённых дат. В `Pict` и `FinishedWork` добавляется `updated_at`; такое же поле, унаследованное от общего `SeoMetadataFields`, добавляется в `Category` и `TagPict`. Существующие записи получают дату применения миграции как исходное время изменения, после чего поля обслуживаются через `auto_now=True`.

Миграция меняет только схему и сохранённое имя прежнего столбца Django; фотографии, связи и публикация записей не изменяются. Дальнейшая синхронизация timestamps при изменении связей выполняется runtime-сигналами, а не миграцией.

## `0029_alter_pict_alt_alter_pict_photo`

Зависит от `pict/0028`. Убирает `blank=True` у `Pict.alt`, поэтому поле становится обязательным в Django ModelForm и административной панели. Существующие пустые строки не заменяются автоматически: миграция не создаёт вымышленные описания и не меняет публикацию записей.

Для `Pict.photo` строковый `upload_to='photos/'` заменяется сериализуемой функцией `pict.models.pict_photo_upload_to`, а допустимая длина сохранённого пути увеличивается до 255 символов. Миграция не перемещает и не переименовывает существующие файлы. Текущая реализация функции использует описание и `Pict.name`; изменение её внутреннего правила не требует новой миграции, поскольку сериализованный путь функции остаётся прежним. Новое правило применяется только при последующей загрузке или замене изображения.

## `0030_alter_pict_name`

Зависит от `pict/0029` и меняет только `verbose_name` поля `Pict.name` с «Имя файла» на «Номер изображения». Тип столбца, уникальность, индекс и все сохранённые номера остаются без изменений.

## `0031_pict_detail_page_fields`

Зависит от `pict/0030`. Добавляет к `Pict` необязательные `page_description`, `seo_h1`, `seo_title`, `seo_description` и временно nullable-поле `slug`. Data-операция пакетно обходит существующие строки по 500 записей, транслитерирует `alt`, добавляет уникальный `name` и сохраняет результат длиной не более 220 символов. Историческое пустое описание получает вид `izobrazhenie-<номер>`.

После заполнения `slug` становится обязательным, уникальным и не редактируемым формой. Обратное применение не пытается восстановить вычисленные значения: при откате добавленные столбцы целиком удаляются. Существующие изображения и M2M-связи миграция не меняет; изменение `updated_at` касается только отображаемой подписи поля.

## `0032_finishedwork_glass_type_finishedwork_paint_color_and_more`

Зависит от `pict/0031`. Добавляет в существующую таблицу готовых работ три столбца: `glass_type`, `skinali_type` и `paint_color`. Исторические строки получают совместимые значения `standard` («Обычное»), `print` («Печать») и пустой цвет; фотографии, публикация и необязательная связь с номером изображения не меняются.

После добавления полей создаётся `CheckConstraint finished_work_fields_match_skinali_type`: печать требует пустого цвета и допускает необязательный номер изображения, покраска требует непустой цвет и отсутствие номера, прозрачный тип требует отсутствия обоих зависимых значений. Новых таблиц, индексов и связей миграция не создаёт.

## `pict/0033_alter_contactrequest_request_type`

Добавляет к choices существующего `ContactRequest.request_type` код `quiz` с подписью «Квиз». Длина столбца и хранящиеся заявки не меняются; миграция нужна для согласованного состояния Django и последующей внешней связи приложения `quiz`.

## `pict/0034_pict_is_popular`

Зависит от `pict/0033` и добавляет в существующую таблицу `Pict` булево поле `is_popular` с подписью «Популярное изображение». Значение по умолчанию `False`, поэтому все исторические изображения после применения миграции остаются неотмеченными. Новых таблиц, индексов и связей миграция не создаёт; публичную выборку миграция не меняет.

## `pict/0035_alter_finishedwork_photo`

Зависит от `pict/0034`, заменяет строковый `upload_to='finished_works/'` поля `FinishedWork.photo` сериализуемой функцией `pict.models.finished_work_photo_upload_to` и увеличивает `max_length` пути до 255 символов. Миграция не перемещает и не переименовывает существующие файлы: новое правило применяется только при последующей загрузке или замене, а для исторических оригиналов используется явное действие Django Admin.

## `quiz/0001_initial`

Зависит от `pict/0033` и создаёт четыре таблицы:

- `Quiz` — публикация, hash-триггер, область страниц, кнопка, автопоказ, период повторения и тексты формы/результата;
- `QuizQuestion` — последовательные вопросы трёх типов;
- `QuizOption` — варианты, комплектные static-изображения и необязательная замена через `ImageField`;
- `QuizSubmission` — защищённая связь с квизом, связь один-к-одному с `ContactRequest` и JSON-снимок ответов.

`QuizSubmission.contact_request` удаляется каскадно с заявкой; `quiz` использует `PROTECT`, чтобы история не потеряла источник.

## `quiz/0002_seed_skinali_quiz`

Создаёт включённый квиз `skinali-quiz` из публичной конфигурации LeadForms №2327: шесть вопросов, 23 варианта и ссылки на 13 локальных static-изображений. Начальные настройки: фиксированная кнопка слева, автопоказ через 10 секунд, повтор через 3 дня, мобильный показ, сброс ответов после закрытия и прекращение автопоказа после успешной заявки. Повторное применение после одиночного отката сохраняет существующую карточку и пользовательские правки вместо создания дубликата.

В той же операции включённые `Integration`, содержащие LeadForms и ID `2327`, переводятся в выключенное состояние. Код не удаляется; для каждой затронутой записи создаётся `IntegrationRevision` без автора с причиной отключения и полным снимком. Обратная функция `RunPython.noop` не включает сторонний скрипт и не удаляет пользовательские ответы. Подробный контракт: [встроенный квиз](../quiz/overview.md).

## `sitecontent/0001_initial`

Создаёт единственную системную модель `SiteMenu` и связанные одноуровневые строки `MenuItem`. В той же миграции прежний Python-список переносится в пять включённых пунктов «Основного меню»:

1. «Главная страница» — `/`, порядок 10;
2. «Каталог скинали» — `/skinali/`, порядок 20;
3. «Наши работы» — `/foto-skinali-iz-stekla/`, порядок 30;
4. «Услуги дизайнера» — `/designer`, порядок 40;
5. «Связаться с нами» — `/about/`, порядок 50.

Миграция не зависит от `pict`: URL сохраняются как текстовые значения, а связь с моделями каталога не создаётся. Обратная data-миграция удаляет системное меню и каскадно его пункты. Текущая модель, admin и публичный вывод описаны в [sitecontent/overview.md](../sitecontent/overview.md).

## `sitecontent/0002_sitepage`

Создаёт отдельную таблицу `SitePage` с неизменяемым строковым первичным ключом `code`, необязательным `seo_title` длиной до 200 символов и необязательным `seo_description` длиной до 320 символов. Data-операция добавляет пять пустых системных записей:

1. `home` — «Главная страница»;
2. `skinali` — «Каталог скинали»;
3. `finished_works` — «Наши работы»;
4. `designer` — «Услуги дизайнера»;
5. `about` — «Связаться с нами».

Пустые значения намеренно сохраняют прежние встроенные метаданные публичных страниц. Миграция зависит только от `sitecontent/0001_initial` и не создаёт связи с меню или моделями `pict`; повторное использование полей между приложениями реализовано абстрактным Python-классом и не меняет схему таблиц `Category` и `TagPict`.

## `sitecontent/0003_sitepage_updated_at`

Добавляет в `SitePage` служебный `updated_at` с `auto_now=True`. Пять существующих системных карточек получают дату применения миграции; далее поле служит сохранёнными часами `lastmod` постоянных страниц. Пользовательская форма admin по-прежнему содержит только SEO-title и meta description.
