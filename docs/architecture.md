# Архитектура проекта

## Назначение

Информационные таблицы страницы «Цена» хранятся в `sitecontent.PriceTable` и связанных
через FK с `CASCADE` `PriceTableRow`, независимо от тарифов калькулятора. Их редактируют
суперпользователи в «Управлении сайтом» через таблицу с inline-строками. Представление
`calculator.views.price()` загружает опубликованные непустые таблицы со строками и выводит
их под калькулятором даже при его отключении. Публичных маршрутов и API для таблиц нет;
единственный новый маршрут — защищённый admin POST перестановки. Серверная перестановка
категорий и таблиц использует общий `skinali/admin_order.py`, клиентская — прежний
`admin-order.js`, дополненный `refresh()` для новых inline-строк. Общие signals обновляют
часы страницы «Цена» при изменении таблиц/строк; сортировка делает это явно.
[Подробности и проверки](sitecontent/price-tables.md).

Подсказки «?» калькулятора являются содержимым БД: `CalculatorTariffs` хранит `panels_hint`, `glass_type_hint`, `decoration_type_hint`, `stair_lifting_hint`, а каждая `CalculatorService` — своё `hint`. Подсказки общих параметров редактируются в «Тарифах и услугах», подсказки дополнительных услуг — только в формах добавления/изменения услуги. В inline общей карточки поле услуги отсутствует; сохранение тарифов сохраняет его прежнее значение. Миграция `calculator/0014_public_hints` переносит прежние тексты из шаблона в существующие записи. `public_configuration()` передаёт обрезанный по краям текст с уже загруженными параметрами; общий include показывает значок только при непустом значении и безопасно сохраняет переносы строк. Тарифы и вычислитель не зависят от подсказок; дополнительных связей, запросов на каждую услугу и маршрутов нет.

Публичный калькулятор находится в `calculator/views.py`, `public.py` и `urls.py`: страница `/price/` подключена перед маршрутами `sitecontent` и `pict`, использует общие SEO-функции `pict.views`, сессионное избранное и `pict/base.html`. `public_configuration()` передаёт только необходимые публичные данные через `json_script`; `price-engine.js` выполняет десятичную арифметику в браузере, `price.js` управляет вводом и результатом. Изменение полей не обращается к серверу. Миграция `sitecontent/0010_price_page` добавляет SEO-карточку и пункт меню «Цена»; маршрут входит в `StaticViewSitemap`. Общий переключатель отключает форму и выдачу тарифов, сохраняя страницу с контактной ссылкой. [Подробности](calculator/overview.md#публичная-страница-цена).

`calculator/sharing.py` создаёт и проверяет подписанные ссылки на расчёт: `POST /price/share/` валидирует публичные параметры общей серверной формулой и выдаёт `/price/?calculation=...`, без записи в БД. GET восстанавливает параметры через безопасный JSON и пересчитывает сумму по действующим тарифам. Отдельные salt/версия, CSRF, границы ввода и запрет индексации защищают обмен; недоступные варианты не заменяются автоматически. Кнопки сервисов, копирование, уведомления и асинхронная подготовка ссылки переиспользуют общий `image-sharing.js`. [Контракт](calculator/overview.md#поделиться-расчётом).

Размеры панелей ограничены общей константой `MAX_PANEL_DIMENSION_MM=6000`: серверные `Panel`/`PanelForm` и публичный `price-engine.js` принимают ширину и высоту от 1 до 6000 мм включительно. Публичный JSON передаёт предел как `max_panel_dimension_mm`, шаблоны используют его в атрибутах полей и общем описании диапазона. Диапазон этажа подъёма 2–12 задают константы `MIN_STAIR_FLOOR=2` и `MAX_STAIR_FLOOR=12`, общие для серверного ввода, admin-формы и публичного JS; начальное значение равно минимуму. Количества услуг используют собственные сохранённые пределы.

`calculator` содержит две независимые singleton-модели с кодом `skinali`: `CalculatorSettings` («Настройки калькулятора») хранит общий показ `is_enabled` и акционные настройки, а `CalculatorTariffs` («Тарифы и услуги») — параметры материалов и подъёма, связи услуг и правил лестницы. Миграция `0010` переносит текущее состояние флага в отдельную таблицу, сохраняя тарифы, PK и связанные записи; откат возвращает флаг в объединённую карточку. Обе карточки используют общий `CalculatorCardAdmin` и шаблон ссылок, сохраняются независимо и доступны только активному суперпользователю. Публичная страница «Цена» (`/price/`) получает конфигурацию при загрузке и выполняет дальнейшие вычисления в браузере; общий флаг управляет формой и выдачей тарифов. Проверочный расчёт работает независимо от общего флага.

`CalculatorSettings.marketing_discount_description` хранит необязательное многострочное описание акции до 2000 символов. Поле добавлено миграцией `0015` с пустым default, редактируется под маркетинговым процентом через `CalculatorSettingsAdminForm`. `public_configuration()` передаёт обрезанный по краям текст в публичный шаблон как заголовок блока итоговой цены. HTML экранируется, переносы сохраняются; пустое описание скрывает видимый заголовок, сохраняя доступное название карточки. Вычисления от описания не зависят.

Акционные настройки `CalculatorSettings.area_discount_percent` и `marketing_discount_percent` хранят проценты с нейтральными значениями 0%. Миграция `0011` ввела скидку по площади и маркетинговый коэффициент, а `0012` перевела коэффициент в процент скидки с сохранением эквивалента до двух знаков. Расчёт читает настройки одним запросом: при общей площади строго больше 2 м² процент по площади последовательно снижает стоимость каждого следующего м² стекла и декорирования, а маркетинговая скидка восстанавливает цену для зачёркивания из округлённого итога делением на `(1 − процент / 100)`. Геометрическая сумма вычисляется без обхода всех метров; услуги и подъём не получают скидку по площади. `CalculationResult` возвращает сумму скидки и сравнительную цену, которую проверочный шаблон показывает отдельно от итога к оплате. Публичная страница повторяет эти правила в `price-engine.js`, получая `area_discount_threshold` из серверной константы. При площади до 2 м² включительно оба расчёта возвращают нулевую скидку; миграция `0013` обновляет подсказку без изменения сохранённых значений; [точные правила](calculator/overview.md#акционные-настройки).

`CalculatorService.max_quantity` — nullable индивидуальный максимум ручного количества услуги, добавленный миграцией `0016` без изменения прежних тарифов и пределов. Миграция `0017` переводит поле в Decimal(11,2), округляя старые максимумы до сотых с сохранением допустимого диапазона. Модельные константы точности задают единый шаг 0,01 для ручных количеств и максимумов в редакторе, проверочном расчёте, публичном JSON/HTML и JS-движке; целый режим сохраняет шаг 1 и отображение без дроби. Общая `service_quantity_limit()` задаёт верхнюю границу для `CalculationForm`, формулы и публичного JSON; сайт использует её в HTML `max` и десятичном JS-движке. Для фиксированной цены, включённой услуги и количества по площади максимум не применяется и сохраняется при переключении режима. Геометрия отдельных панелей сохраняет полную точность; общая расчётная площадь перед ценами, скидкой и услугами по м² округляется до сотых по HALF_UP. Константа `AREA_DECIMAL_PLACES` передаётся в публичный JSON; Python и BigInt-движок выполняют одинаковое округление после суммирования панелей. Промежуточные денежные вычисления не округляются, итог округляется вверх до целого.

`CalculatorService.fixed_price` задаёт платную фиксированную сумму за весь заказ. В форме остаётся только чекбокс подключения, а расчёт берёт количество 1 независимо от клиентского ввода, площади и числа панелей. `requires_manual_quantity` объединяет выбор режима для формы и расчёта. Переключение фиксированного режима сохраняет прежние настройки ручного количества/площади, включённые услуги сохраняют нулевую стоимость. Миграция `0008` добавляет выключенный по умолчанию флаг без изменения тарифов существующих услуг.

Перетягивание категорий и блоков дополнительных услуг использует общий `pict/static/skinali/js/admin-order.js` и `css/admin-order.css`. Категории сохраняют порядок своим существующим AJAX-адаптером. Услуги используют `calculator/js/admin-service-order.js`: перестановка карточек обновляет скрытые `position` в formset, порядок и цены сохраняются атомарно стандартной кнопкой настроек. Отдельный маршрут сортировки услуг не добавлен. Поле порядка исключено из редактора услуги, новые услуги из admin добавляются в конец списка.

Единицы общих услуг калькулятора вынесены в `MeasurementUnit`: название, обозначение и порядок. `CalculatorService.unit` — nullable FK с `PROTECT`; пустое старое обозначение сохраняется как отсутствие ссылки. Справочник редактируется в отдельном разделе admin, а в услуге используется выпадающий список. Миграция `0007` переносит прежние обозначения, сохраняя нестандартные и объединяя одинаковые. Услуги читаются с `select_related('unit')`, результат содержит строковое обозначение; цены и источник количества от выбора единицы не меняются. Измерение геометрии и уникальная формула лестницы сохраняются.

Общие услуги калькулятора хранятся в `CalculatorService` с FK `settings` на `CalculatorTariffs`: название, подписи, тариф за единицу, показ, включённый режим, порядок и параметры количества. Замер и монтаж — отдельные услуги. Карточки в «Тарифах и услугах» имеют действия редактирования и удаления справа; новая услуга добавляется из того же списка. Стандартный редактор услуги скрыт из меню, обычное сохранение возвращает в «Тарифы и услуги». Миграция `0006` переносит семь исходных услуг до удаления прежних полей. `ServiceSelection` задаёт единый ввод услуги и количества; формула всегда «цена за единицу × количество», площадь вычисляется сервером. Платные услуги подключаются чекбоксом, включённые показываются без ввода и дают нулевую строку. Список и порядок едины для настроек, проверочной формы и сметы. Стекло, декорирование и лестница остаются уникальными разделами. CRUD услуг защищён теми же правами, CSRF и журналом, что и остальные настройки.

Отдельное приложение `calculator` предоставляет группу admin «Калькулятор скинали»: два самостоятельно заполняемых справочника, отдельные карточки общих настроек и тарифов/услуг, а также проверочный расчёт с расшифровкой. `calculation.py` — единый серверный модуль площади и стоимости, `forms.py` строит ввод из настроек и FormSet панелей. Для лестницы отдельно вводятся этаж и число панелей в пределах сохранённой таблицы, максимум 6: к стандартной стоимости прибавляется доплата за этажи сверх порога с коэффициентом сложности. Связанная с `CalculatorTariffs` модель `StairLiftingRule` хранит последовательные столбцы для 1–6 панелей; форма настроек показывает их горизонтальной таблицей через `widgets.py` с кнопками добавления/удаления последнего столбца. Замена правил атомарна, типы и ограничения проверяются сервером и БД. Миграция `0004` переносит прежние четыре пары значений до удаления фиксированных полей. Форма и расчёт получают актуальные правила через `get_stair_lifting_rules()`, включая максимум и подсказку поля «Панелей». Этаж по умолчанию равен 2, допустим диапазон 2–12. Число панелей для подъёма независимо от количества геометрических строк. Общий итог округляется вверх до целого. Основной маршрут `calculator_calculatortariffs_calculate` и совместимый alias `calculator_calculatorsettings_calculate` находятся внутри AdminSite, требуют активного суперпользователя и CSRF для POST; пробные расчёты не сохраняются. Публичная страница «Цена» рассчитывает стоимость в браузере; POST `/price/share/` проверяет параметры и выдаёт подписанную ссылку, отдельного API получения цены нет. Модели не связаны с типами готовых работ. Общие mixin доступа суперпользователя и перехода в singleton вынесены из `sitecontent.admin` в `skinali/admin_mixins.py` и используются обоими приложениями. Подробности: [Админка калькулятора](calculator/overview.md).

`Skinali` — серверный Django-проект с приложением каталога `pict`, отдельным приложением управляемого содержимого `sitecontent` и встроенным приложением квиза `quiz`. Данные хранятся в SQLite, изображения каталога — в `skinali/media/photos/`, фотографии готовых работ — в `skinali/media/finished_works/`, страницы собираются Django-шаблонами. `Pict.name` хранит уникальный числовой номер изображения и под этой подписью показывается в Django Admin. Каждый опубликованный `Pict` имеет индексируемую индивидуальную страницу со стабильным slug, управляемыми SEO-полями, кешированным превью со ссылкой на полноразмерный оригинал и похожими изображениями. Новые оригиналы каталога получают латинское имя из обязательного описания и значения поля «Номер изображения»; это правило находится в модели `Pict` и одинаково действует при любой штатной загрузке через Django. Для исторических оригиналов `PictAdmin` предоставляет явное массовое переименование с безопасным обновлением поля, удалением старого файла и очисткой его кешированных превью.

Замена фотографии или удаление `Pict`/`FinishedWork` назначает очистку прежнего оригинала и связанных миниатюр через signals → `services/photo_cleanup.py` → `transaction.on_commit`. После commit сервис проверяет ссылки всех файловых полей БД; используемые и неопубликованные файлы сохраняются, а rollback отменяет удаление. Admin-переименование использует тот же механизм. Накопившиеся оригиналы без ссылок находятся одноразовой командой `cleanup_unused_photos`: по умолчанию только отчёт, удаление — явным `--delete`, с защитным возрастом в сутки. Подробности: [Очистка фотографий](pict/photo-cleanup.md).

SEO-интерфейс admin для изображений, категорий, тегов, постоянных страниц и статей вынесен в `sitecontent/admin_seo.py`: оба admin-модуля используют общий mixin, а общий CSS/JS из статики `pict` обеспечивает ширину полей, рекомендации длины и живой счётчик без запросов к серверу. Модели, лимиты и публичные метаданные не изменяются; [подробности](sitecontent/admin-seo.md).

Связь `FinishedWork.catalog_image` используется в обе стороны публичного интерфейса. В модальном окне каталога ссылка «В интерьере · N фото» открывает опубликованные работы выбранного рисунка поверх исходной карточки, а на индивидуальной странице эти фотографии находятся под рисунком в левой колонке. Общий ORM-помощник `with_published_finished_works()` загружает связи текущей страницы одним дополнительным запросом; общие шаблоны миниатюр/работ и существующий Fancybox не требуют новых таблиц, миграций или URL. Контракт описан в [views.md](pict/views.md#готовые-работы-выбранного-изображения).

## Структура

Единый `THUMBNAIL_BACKEND` подключает `pict/thumbnails.py`: превью поля `Pict.photo` получают имя `хеш-номер.jpg` во всех публичных разделах и admin. Номер берётся из экземпляра `Pict`, остальные модели сохраняют штатные имена. Старые копии остаются доступны, новые создаются постепенно в том же KV-хранилище и очищаются существующим механизмом вместе с оригиналом. Backend также проверяет наличие файла и восстанавливает отсутствующее превью и метаданные после сброса кеша из другого процесса, сохраняя оригинал и другие размеры. Схема БД и маршруты не меняются; [подробности](pict/thumbnails.md).

## Основной поток запроса

Публичные списки каталога, тегов, готовых работ и статей используют общий `pict/includes/paginator.html` и тег `pagination_items` из `pict/templatetags/pagination.py`. Он строит компактный ряд без полного обхода страниц и запросов к БД; кликабельные `...` ведут на среднее соседних номеров с округлением вниз. Оформление «Лёгкая» убирает постоянные рамки и заливку обычных ссылок, сохраняя тёмный овальный текущий пункт и параметры фильтров. Подробности: [Общая пагинация](pict/pagination.md).

1. `skinali/skinali/urls.py` направляет публичные запросы в `pict/urls.py`, служебный префикс `/quiz/` — в `quiz/urls.py`, `/sitemap.xml` — во встроенное sitemap-представление с `pict/sitemaps.py`, а `/robots.txt` — в небольшой текстовый ответ с правилами обхода и абсолютным адресом карты сайта.
2. `pict/urls.py` выбирает class-based или function-based view.
3. `pict/views.py` получает данные через ORM-модели из `pict/models.py`; каталог и готовые работы проходят через общую выборку `published()`. Главная, общий каталог, готовые работы, дизайнер и контакты точечно читают два SEO-поля соответствующей `sitecontent.SitePage`. Сигналы `pict/signals.py` обновляют сохранённые часы изменившихся публичных разделов при обычном сохранении, удалении и изменении M2M-связей.
4. При наличии `q` форма проверяет нормализованный запрос. Перед валидным текстовым поиском `SkinaliMix` одним коротким запросом читает глобальный флаг `sitecontent.CatalogSearchSettings` без межзапросного кеша и передаёт его в `pict/search.py`. Включённый режим использует AND-условия по точным тегам/синонимам и леммам `TagSearchLemma`, без фрагментов; выключенный — частичное вхождение в теги и синонимы без вызова морфологии. Только наиболее вероятный разбор `pymorphy3` применяется к словам запроса; словарь лениво переиспользуется в процессе и ограниченный LRU-кеш хранит до 2048 слов. Номер изображения, невалидная форма и обычный каталог настройку не читают. Все слова и способы совпадения входят в один SQL списка; точные совпадения имеют больший вес в обоих режимах.
5. View передает queryset и дополнительный контекст в шаблон из `pict/templates/pict/`; постоянное меню больше не дублируется в представлениях.
6. Context processor `sitecontent.context_processors.site_navigation` передаёт ленивый упорядоченный QuerySet видимых пунктов и использующую его коллекцию URL. Результат одного ORM-запроса повторно применяется в шапке, подвале и проверке адреса, которая позволяет шаблону главной скрывать карточку перехода в «Наши работы» вместе с соответствующим пунктом меню; неиспользуемый контекст не обращается к БД, межзапросного кеша нет. Отдельный `pict.context_processors.site_identity` без запросов к БД передаёт единые публичные реквизиты и абсолютные URL от `PUBLIC_SITE_ORIGIN`.
7. Ленивый `quiz.context_processors.public_quiz` при обращении из `pict/base.html` загружает включённый квиз, вопросы и варианты тремя запросами. Шаблон добавляет локальный CSS, `<dialog>`, фиксированную боковую кнопку с управляемыми стороной, текстом и необязательной media-иконкой, а также JavaScript; неподходящий путь или выключенная запись не выводятся. Область страниц квиза поддерживает точное совпадение и конечные маски `/*` для раздела со всей вложенностью через явный параметр общего `pict.page_paths`; интеграции продолжают использовать только точные пути.
8. Общие шаблоны каталожной карточки и готовой работы запрашивают у `sorl-thumbnail` кешированные превью: каталог ограничивает ширину 760 px с сохранением пропорций, а квадратные карточки работ используют центральный кроп 760 × 760 px. Первый запрос создаёт производный файл в `media/cache/thumbnails/`, последующие используют общий кеш. Сетка каталога использует вариант 760 px; `data-src` модального окна обращается к отдельному маршруту и только при открытии создаёт вариант шириной до 1920 px с `quality=90`. Индивидуальная страница использует тот же крупный вариант, а оригинал сохраняется как ссылка для отдельного открытия. Для готовых работ Fancybox по-прежнему открывает оригинал. Миниатюры каталога и полной галереи готовых работ при наведении или клавиатурном фокусе показывают одинаковую внутреннюю белую рамку; во время нажатия её общий псевдоэлемент получает широкую внутреннюю белую тень. В модальной карточке каталога адрес оригинала преобразуется браузером в абсолютный URL и вместе с номером изображения передаётся штатным ссылкам публикации Telegram, Viber и WhatsApp; серверные API и ключи для этого не используются.
9. Шаблон формирует HTML; `{% static %}` всегда выдаёт корневые адреса `/static/...`, поэтому ресурсы одинаково разрешаются на главной и вложенных страницах. Общий CSS-компонент `.catalog-categories` оформляет десктопные кнопки категорий каталога, фильтра готовых работ и типов скинали; невыбранная кнопка при наведении или клавиатурном фокусе за `.35s` заполняется слева направо светлым градиентом без изменения заданной рамки. Кнопка обратного звонка в основном меню имеет сплошной зелёный фон без обводки, при наведении меняет цвет, а во время нажатия сжимается на 10%. Медиа в режиме `DEBUG` обслуживаются корневым URLconf. В preview- и production-профилях `DEBUG=False`, Debug Toolbar и его маршрут не подключаются, а статика собирается в `skinali/staticfiles/` для отдачи внешним веб-сервером.

Технический HTTP-домен Hostland работает в отдельном профиле `preview`: он требует собственные секрет и белый список host, но не включает HTTPS-only cookies до появления сертификата. `skinali.middleware.SearchEngineIndexingMiddleware` добавляет `X-Robots-Tag: noindex, nofollow` ко всем его ответам, а `robots.txt` возвращает полный запрет обхода без sitemap. После переключения на `production` оба ограничения исчезают, а HTTPS-защита cookies и редирект включаются автоматически.

Sitemap содержит постоянные страницы, отдельный HTML-URL каждого опубликованного изображения, а также категории и теги с опубликованными изображениями. Постоянная секция одним запросом получает сохранённый `SitePage.updated_at`; каждая динамическая секция использует один queryset, который стандартный пагинатор Django выполняет как COUNT и выборку текущей страницы. Для `lastmod` справочника выбирается более поздняя дата из собственного `updated_at` и максимального `Pict.updated_at`, а у страницы изображения используется её собственный timestamp; из строк моделей загружаются только slug и время. Снятые с публикации изображения, пустые категории, пустые теги и элементы только со снятыми с публикации изображениями в XML не попадают. Изменения изображений, готовых работ, справочников, публикации, категорий, тегов и цветов через штатный ORM синхронно обновляют соответствующие часы; сетевой запрос не выполняется.

Индексируемые страницы изображений, категорий и тегов поддерживают управляемые H1, основу SEO-title и meta description. Общие поля приходят из абстрактной `SeoPageContent`; `SeoLandingContent` дополнительно даёт категориям и тегам вводный текст, а `Pict` имеет собственное описание страницы и стабильный slug. Отдельной таблицы и дополнительных запросов нет. Пустые значения сохраняют автоматические уникальные метаданные, а представления добавляют к title бренд и, для списков, номер страницы.

Семь постоянных разделов основного меню имеют отдельные системные записи `SitePage`: главная, каталог, цена, готовые работы, услуги дизайнера, статьи и контакты. Каждая запись содержит два редактируемых поля — основу SEO-title и meta description — и служебный `updated_at`; технический код является неизменяемым первичным ключом. Пустые поля сохраняют встроенные метаданные, а заполненный title получает номер страницы и бренд в представлении. Для одной публичной страницы выполняется один короткий запрос только двух SEO-столбцов; при нагрузке 10–20 посетителей отдельный кеш для него не нужен. `SitePage` и каталожная `SeoLandingContent` наследуют одинаковые поля и обновление timestamp от абстрактной `sitecontent.SeoMetadataFields`, поэтому ограничения не дублируются.

Все индексируемые публичные страницы, кроме корневой, получают видимые хлебные крошки и соответствующий `BreadcrumbList` JSON-LD из одного контекстного списка. Canonical и абсолютные URL структурированных крошек строятся от `PUBLIC_SITE_ORIGIN`, поэтому не зависят от `Host` входящего запроса; видимые ссылки остаются относительными. Дополнительных запросов к БД нет, а динамические названия безопасно экранируются. Страницы с `noindex,follow` сохраняют только визуальную цепочку; структурированные данные для них не выводятся.

Главная страница выводит в `<head>` JSON-LD-граф `WebSite` и `Organization`. Сущности получают стабильные `@id` от официального origin и связаны через `publisher`; организация содержит название «ОДИУМ», основной телефон, email, абсолютный URL логотипа и официальные профили Instagram и ВКонтакте. Адрес намеренно отсутствует. Видимые реквизиты базового шаблона и JSON-LD используют один `SITE_IDENTITY`, поэтому изменение контактов не требует синхронных правок в нескольких шаблонах.

Публичный production-вариант `robots.txt` запрещает обход настраиваемого пути admin, POST-обработчика контактных заявок и служебного префикса квиза `/quiz/`, сообщает Яндексу о рекламных query-параметрах через `Clean-param` и ссылается на sitemap от `PUBLIC_SITE_ORIGIN`. Все `<loc>` самой XML-карты принудительно используют тот же origin и не зависят от `Host` входящего запроса. По умолчанию публичный origin равен `https://odium.by`; в production допускается только HTTPS. Preview-вариант полностью запрещает обход и дополняется глобальным HTTP-заголовком noindex.

Неизвестные публичные URL при `DEBUG=False` получают полноценную страницу сайта с настоящим HTTP 404 и `noindex,follow`. `pageNotFound()` рендерит `pict/404.html` через обычный `pict/base.html` с объектом `request`, поэтому используются управляемое меню, контакты, подвал, общие диалоги, подходящие текущему пути интеграции/квиз и счётчик избранного из сессии. В контенте находятся оригинальная прозрачная PNG пользователя `static/skinali/images/404.png`, текст ошибки и относительные ссылки на главную и каталог; отдельный `not-found.css` задаёт адаптивную компоновку. Необработанные production-ошибки по-прежнему получают автономную страницу с HTTP 500, `noindex,nofollow`, нейтральным сообщением и ссылкой на главную без раскрытия технических деталей. Только 500 использует аварийную оболочку `pict/error_base.html` с CSS и настроенным логотипом, рендерится без объекта `request` и не задействует context processors, меню, интеграции и БД. Обе страницы не выводят canonical и JSON-LD.

Для избранного используется встроенная Django-сессия с backend `signed_cookies`. Браузер отправляет POST-запрос переключателю, `pict/views.py` сохраняет список первичных ключей `Pict` под ключом `favorite_pict_ids`, а Django возвращает обновленную подписанную cookie без записи сессии в SQLite. `/favorites/` загружает актуальные изображения по этим ключам и всегда отдаёт `noindex,follow` с self-canonical. Маршрут не запрещён в `robots.txt`, поэтому робот может прочитать meta-директиву. Отдельная модель избранного и авторизация для этого сценария не используются.

Общий `pict/services/favorites.py` нормализует список, ограничивает его 50 изображениями и формирует бессрочные подписанные ссылки `/favorites/shared/?data=…` с версией, ID и отдельной меткой подписи. Подборки целиком находятся в URL и не записываются в БД. GET проверяет ссылку, `favorites-import.js` автоматически отправляет отдельный POST с CSRF, а сервер объединяет список с cookie получателя в пределах свободных мест; не поместившаяся часть остаётся для повтора. Переход через `location.replace()` завершает сценарий на `/favorites/` без токена, а существующий Toast показывает результат. Подробности: [Избранное и обмен подборками](pict/favorites.md).

При переполнении проверенный токен остаётся в cookie до повторной попытки: `/favorites/` показывает кнопку «Добавить всё в моё избранное». После удаления лишних карточек посетитель отправляет ту же общую форму `includes/favorites_import_form.html`; успешный импорт очищает отложенный токен. Эта форма также раскрывается на исходной странице при сетевом сбое автоматического POST. Серверного хранилища отложенных подборок нет.

В той же cookie хранится ограниченный исходной подборкой список `pending_favorites_added_ids` для учёта фактически импортированных изображений. Общее количество, добавленная часть и остаток отображаются отдельно; после удаления сервер пересчитывает их, а JavaScript обновляет подписи. Повторы и исходные совпадения не увеличивают число новых изображений, завершение очищает токен и историю добавления.

POST `/favorites/clear/` очищает только избранное текущей сессии, сохраняя отложенный импорт и остальные данные cookie. После перенаправления на `/favorites/` полученную подборку можно добавить заново. Две формы действий центрированы в общем ряду; добавление переиспользует зелёный стиль «Купить», очистка — серый стиль удаления карточки. Схема БД и изображения не затрагиваются.

Контактная форма в одной короткой транзакции сохраняет `ContactRequest` и через общий сервис отдельные доставки `pending` каждому получателю подходящих включённых `sitecontent.LeadConnection`. Для покупки изображения сервер проверяет скрытый первичный ключ `Pict`, сохраняет связь и отдельный снимок номера. Квиз в той же транзакции добавляет `QuizSubmission` со снимком вопросов и ответов. Заказ из калькулятора использует `CalculatorOrderContactForm` на основе общей телефонной формы, отдельный тип `calculator_order` и read-only поле `ContactRequest.calculation_url` (миграция `pict/0039`). `calculator.public.get_public_calculator()` переиспользуется страницей, ссылками и проверкой формы; `calculator.sharing.validate_calculation_share_url()` проверяет собственный origin, подпись и действующие параметры с серверным пересчётом, затем возвращает каноническую ссылку. Создание заявки выполняется прежним `contact_submit`, без нового endpoint и без доверия к клиентской цене. Диалог калькулятора использует общий HTML/JS контактных форм, а URL получает из существующего `/price/share/`; устаревший ответ после изменения формы игнорируется. При отсутствии подключений заявка сохраняется без доставок. Веб-запрос не обращается к внешним сервисам. Одноразовая management-команда атомарно переводит готовые задачи в `processing`, завершает запись в SQLite и только затем выполняет запрос через адаптер Telegram или SMTP. Ошибка настройки отдельного подключения не блокирует остальные. Результат фиксируется отдельным коротким обновлением с проверкой владельца попытки; временные ошибки получают расписание повторов, постоянные — статус `failed`. Такой поток не держит SQLite-транзакцию открытой во время сети и не использует Redis, Celery или фоновые потоки web-процесса.

## Основные сущности

- `sitecontent.LeadConnection` — подключение сервиса, получатели, маршрутизация и зашифрованные секреты. Каждая `ContactRequestDelivery` принадлежит одному подключению и хранит адрес получателя; обычные доставки связаны с заявкой, тестовые — с UUID группы. Подключение с историей защищено от удаления.

- `SeoMetadataFields` — общий абстрактный набор SEO-title, meta description и служебного времени изменения; `SitePage` — пять системных SEO-карточек и часов постоянных разделов. `SiteMenu` — единственная системная карточка «Основное меню»; `MenuItem` — упорядоченная, видимая или скрытая одноуровневая ссылка, общая для шапки и подвала. [Подробности](sitecontent/overview.md).
- `Integration` — управляемые суперпользователем HTML/JS-вставки в три области базового шаблона; `IntegrationRevision` хранит снимки настроек и автора через `AUTH_USER_MODEL`. Одна интеграция имеет много версий. [Подробности](pict/integrations.md).
- `Quiz`, `QuizQuestion` и `QuizOption` — настройки одного последовательного модального квиза и его редактируемое содержимое; `QuizSubmission` хранит неизменяемый JSON-снимок ответов рядом с общей заявкой. [Подробности](quiz/overview.md).

- `Pict` — изображение с уникальным числовым номером, стабильным slug индивидуальной страницы, файлом, описанием, необязательными SEO-переопределениями, датой добавления, флагом публикации и выключенным по умолчанию ручным признаком популярности; признак популярности пока хранится для будущего отбора и не меняет публичные выборки.
- `FinishedWork` — готовая работа с именем, описанием, одной фотографией, фиксированными типами стекла/скинали, условным цветом покраски и независимым флагом публикации; новый файл фотографии получает латинское имя в нижнем регистре из названия работы, а исторические файлы переименовываются явным действием admin. Для печати работа может ссылаться на одно изображение `Pict`, а одно изображение каталога может использоваться во многих работах. Типы хранятся кодами в той же таблице без отдельных справочников.
- `Category` — категория с управляемой позицией и необязательным SEO-контентом публичной страницы; порядок меняется перетягиванием в admin и применяется в публичной навигации, связь `Pict ↔ Category` многие-ко-многим.
- `Color` — цвет; связь `Pict ↔ Color` многие-ко-многим.
- `TagPict` — основной поисковый тег с автоматически поддерживаемым уникальным нормализованным значением и необязательным управляемым SEO-контентом публичной страницы; связь `Pict ↔ TagPict` многие-ко-многим.
- `TagAlias` — однословный поисковый синоним одного `TagPict`; изображения напрямую с синонимами не связываются.
- `TagSearchLemma` — служебные леммы слов одного `TagPict` или одного `TagAlias`; check constraint разрешает ровно одного владельца, каскадные FK и уникальные пары владельца/леммы поддерживают согласованность индекса. Сохранение поискового поля владельца и индекса атомарно; миграция `0038` заполняет исторические строки. Команда `rebuild_search_lemmas` восстанавливает индекс после bulk-операций или обновления словаря, без изменения исходного контента.
- `sitecontent.CatalogSearchSettings` — единственная системная карточка «Настройки сайта» для глобальных типизированных параметров. Сейчас группа «Поиск по каталогу» содержит переключатель механизма поиска; дальнейшие параметры группируются по назначению. Внутреннее имя модели, PK `catalog` и admin-адрес сохранены. Check constraint ограничивает таблицу одной строкой; миграция `sitecontent/0008` создаёт включённый флаг, а `0009` переименовывает карточку в состоянии Django. Суперпользователь меняет checkbox в «Управлении сайтом → Настройки сайта», а список «Ключевые слова» содержит ссылку «Настройки сайта». Общий `SingletonSiteContentAdminMixin` переиспользует переход из списка и запрет удаления между этой карточкой и меню. Индекс лемм обновляется при сохранении контента в обоих режимах.
- `ContactRequest` — запись валидной заявки с типом формы, именем, необязательными телефоном/email, вопросом/комментарием, временем создания и необязательным временем первого просмотра в admin; заявка покупки дополнительно хранит необязательную связь с `Pict` и снимок его номера.
- `ContactRequestDelivery` — состояние доставки заявки по отдельному каналу, история попыток и подтверждение внешним ID сообщения; сочетание заявки и канала уникально.

Подробная схема полей и обратных связей: [pict/models.md](pict/models.md).

## Пользовательские сценарии

- `/` — главная страница; прежний `product-number` перенаправляется в новый поиск `/skinali/?q=...`.
- `/skinali/` — опубликованная часть каталога с пагинацией по 30 изображений; без `q` поддерживает фильтр `color`, с `q` выполняет глобальный поиск.
- `/price/` — страница «Цена» с локальным расчётом размеров панелей, материалов, услуг, подъёма и акций; целый итог и зачёркнутая цена. GET/HEAD возвращают HTML и безопасный JSON конфигурации, остальные методы — 405. Выключенный или ненастроенный калькулятор заменяется ссылкой на контакты.
- `/skinali/image/<slug>/` — индексируемая индивидуальная страница опубликованного изображения с полноразмерным оригиналом, покупкой, избранным, классификаторами, похожими изображениями, canonical, `BreadcrumbList` и `ImageObject`; неизвестная или снятая с публикации запись возвращает 404.
- `/skinali/<slug_cat>/` — без `q` показывает опубликованные изображения категории с опциональным фильтром цвета и управляемыми SEO-текстами; с `q` категория и цвет игнорируются, а поиск остается глобальным.
- `/tag/<tag_slug>/` — глобальная выборка опубликованных изображений выбранного тега с пагинацией по 30, счетчиком, управляемыми SEO-текстами и полной каталожной карточкой; категория, цвет и поиск здесь не применяются. Существующий пустой тег возвращает HTTP 200 с пустым состоянием и `noindex,follow`, неизвестный slug — 404.
- `/sitemap.xml` — главная, каталог, цена, готовые работы, дизайнер, статьи, контакты, отдельные страницы опубликованных изображений и статей, непустые категории и непустые теги; поиск, фильтры, пагинация и персональные/служебные URL исключены.
- `/robots.txt` — правила обхода технических маршрутов и ссылка на `/sitemap.xml`; GET и HEAD возвращают текстовый ответ, остальные методы отклоняются.
- `/favorites/` — персональный для текущей браузерной сессии список опубликованных избранных изображений с `noindex,follow` и self-canonical; снятые с публикации записи удаляются из сессии. Кнопка в конце непустого списка передаёт в Telegram, Viber или WhatsApp только текст с актуальными номерами оставшихся карточек, без ссылок.
- `/favorites/toggle/<pict_id>/` — POST-переключатель состояния изображения в избранном; используется JavaScript-кнопками страницы и Fancybox.
- `/contact/request/` — общий POST-обработчик формы обратного звонка, формы с вопросом, формы с обязательным email и формы покупки выбранного изображения; валидные данные сохраняются в `ContactRequest` и ставятся в общую устойчивую очередь, которую обрабатывает отдельная management-команда.
- `#popup:skinali-quiz` — локальный hash-триггер модального квиза; автопоказ с начальными значениями 10 секунд и 3 дня управляется через admin и `localStorage`. `/quiz/skinali-quiz/submit/` принимает валидированную финальную форму, создаёт заявку типа `quiz`, снимок ответов и доставки подходящим подключениям.
- `/foto-skinali-iz-stekla/` — фотогалерея опубликованных готовых работ, отсортированная по новизне и разбитая по 30 элементов на страницу; GET-параметр `category` фильтрует работы по категории связанного изображения каталога.
- `/about/` — контактные данные для двух видов заказов и статическая карта зоны обслуживания; `/designer/` — страница услуг дизайнера с фиксированной ценой `5$` без обращения к внешним сервисам. Прежний `/designer` перенаправляется на `/designer/` стандартным `CommonMiddleware`.
- Прежний тестовый URL `/cats/<id>/` удалён и возвращает штатный HTTP 404; публичные категории доступны только по человекочитаемым `/skinali/<slug>/`.
- `/<DJANGO_ADMIN_PATH>/` — управление каталогом, готовыми работами и единственным квизом, просмотр и поиск сохраненных контактных заявок, а также доступный только суперпользователю раздел «Управление сайтом»; локально используется `/admin/`. Единственная карточка меню редактирует пункты строками, а таблица «Страницы сайта» — по два SEO-поля семи постоянных разделов без возможности добавления и удаления. «Интеграции» остаются отдельным механизмом доверенного кода. В «Управлении сайтом» также доступна «Обработка заявок» с Telegram/email-подключениями, маршрутизацией, тестовыми отправками и состоянием очереди. В списке заявок показываются все каналы и общий статус доставки; карточка заявки квиза дополнительно показывает ответы, отдельная служебная таблица доставок скрыта, а первый просмотр заявки визуально отмечается осветлением имени.

## Внешние и инфраструктурные зависимости

Интеграции не требуют дополнительных пакетов: `{% site_integrations %}` в `pict/base.html` одним запросом выбирает включённые записи, фильтрует точные пути и повторно использует список в head и body. Код не интерпретируется как Django-шаблон. Admin использует собственные шаблоны и не подключает вставки; дополнительная проверка тега исключает namespaces `admin` и `djdt`. Пустой `templatetags/__init__.py` регистрирует пакет шаблонных тегов. Версии доступны через зарегистрированный скрытый admin-раздел и его POST-маршрут восстановления.

Встроенный квиз не загружает LeadForms: исходные 13 изображений находятся в `quiz/static/quiz/images/answers/`, новые замены вариантов — в `media/quiz/options/`, а пользовательская иконка кнопки запуска — в `media/quiz/launcher/`. Кнопка поддерживает четыре управляемых положения: два горизонтальных у нижних краёв и два вертикальных посередине сторон; на мобильном они сводятся к круглой кнопке у выбранного края. Миграция сохраняет, но выключает прежнюю интеграцию LeadForms №2327, чтобы два независимых автопоказа не конкурировали.

Меню и SEO используют штатные средства Django: один ленивый ORM-запрос получает видимые `MenuItem` по системному коду меню, а коллекция адресов использует кеш этого же QuerySet; изменение применяется уже на следующем запросе после сохранения. Постоянная страница отдельно читает два SEO-поля по первичному ключу. Значения ссылок экранируются шаблоном и ограничены белым списком безопасных типов.

- Django `5.2.17` LTS.
- Pillow нужен для `ImageField`.
- `pymorphy3 2.0.6` и закреплённый русский словарь `pymorphy3-dicts-ru 2.4.417150.4580142` выполняют локальную лемматизацию; внешние API и отдельный процесс не нужны. Подробности и ограничения: [Поиск](pict/search.md).
- `nh3 0.3.7` очищает HTML статей на сервере; Quill 2.0.3 и его BSD-лицензия хранятся локально в static.
- `sorl-thumbnail 13.1.0` создаёт и кеширует уменьшенные каталожные превью без дополнительных полей моделей; стандартные `ImageField` продолжают хранить только исходники.
- `django-extensions` и `django_debug_toolbar` по умолчанию подключены только в development-профиле.
- `requests` выполняет HTTPS-вызовы Telegram Bot API из одноразовой management-команды.
- Telegram Bot API и SMTP доставляют заявки сотрудникам. `sitecontent.LeadConnection` задаёт настройки и получателей, `cryptography 50.0.1` шифрует секреты ключом `LEAD_DELIVERY_ENCRYPTION_KEYS` вне базы. Созданное миграцией Telegram-подключение сохраняет прежние `TELEGRAM_*` из окружения. Прокси остаётся строгим, без прямого обхода.
- ASGI и WSGI точки входа доступны одновременно.
- Полный список прямых Python-зависимостей находится в корневом `requirements.txt`; `skinali/requirements.txt` подключает его через `-r ../requirements.txt`. Для Hostland предусмотрен `requirements-production.txt` без инструментов разработки. Назначение пакетов и установка описаны в [project/dependencies.md](project/dependencies.md).

## Статьи «Полезно знать»

`sitecontent.Article` наследует `SeoMetadataFields`, использует общий `sitecontent.querysets.PublicationQuerySet` (также импортируемый `pict.models`) и связан M2M с `ArticleImage`. `sitecontent.urls` подключён перед `pict.urls`: `/polezno-znat/` — опубликованные статьи по 7 с общей пагинацией, `/polezno-znat/<slug>/` — HTML статьи без обложки и даты. Меню едино для шапки/подвала. При создании поле «Адрес статьи» принимает русский или латинский текст; пустое поле использует заголовок. Slug формируется один раз без суффикса существующей функцией `pict.models` через отложенный импорт. Модельная проверка уникальности учитывает также черновики и показывает ошибку у поля адреса в admin-форме; одинаковые заголовки разрешены с разными адресами. При редактировании slug доступен только для чтения, модель сохраняет прежний адрес. Ранее созданные адреса, включая UUID-суффиксы, остаются неизменными. Используется прежний столбец, миграция `0007_article_slug_input` меняет только состояние модели Django.

`sitecontent.views` переиспользует SEO и контекст избранного `pict.views`; `sitecontent.sitemaps.ArticleSitemap` наследует `pict.sitemaps.PublicOriginSitemap`. В корневой XML-карте есть секция `articles`, а список включён в постоянную секцию. «Страницы сайта» содержат новую карточку `article_list`.

Quill работает только в admin: `widgets.py`/`rich_text.py`/`article_media.py` обеспечивают локальные ресурсы, серверную очистку и проверку файлов. HTML очищается при записи, открытии виджета и выводе. Изображения сохраняются в `media/articles/covers/` и `media/articles/content/`, ссылки учитываются в БД; существующие `pict.signals` и `services/photo_cleanup.py` покрывают замену/удаление с защитой транзакций. `cleanup_article_images` ищет забытые загрузки, `cleanup_unused_photos --table articles` — файлы без записей. Полный контракт и все новые файлы: [sitecontent/articles.md](sitecontent/articles.md).
