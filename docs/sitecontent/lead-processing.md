# Обработка заявок

## Назначение и интерфейс

В группе Django Admin «Управление сайтом» зарегистрирована `LeadConnection` с подписью «Обработка заявок». Раздел отвечает за передачу сохранённых заявок сотрудникам через Telegram и email (SMTP). Статусов работы менеджера и автоматических писем клиенту нет. Список показывает название, сервис, получателей, включение, состояние, число ожидающих доставок и ошибок, последнюю успешную отправку.

Подключений каждого сервиса может быть несколько. Карточка содержит основные настройки, получателей по одному на строку, постоянно видимый список типов заявок с отдельным флажком для каждого, поля выбранного сервиса, тайм-ауты и состояние. Флажок «Все типы заявок» отмечает или снимает все пункты; ручное изменение пунктов обновляет общий флажок. Список формируется из `ContactRequest.RequestType`, поэтому новые типы появляются в нём автоматически. Тип `email_message` оставлен для ранее созданных заявок и помечен «форма снята с сайта». Если выбраны все типы, подключение принимает и будущие типы; при частичном выборе — только отмеченные. Пустой выбор не сохраняется. Telegram принимает числовые chat ID и `@username`; email — проверенные адреса сотрудников. Email и Telegram @username приводятся к нижнему регистру, числовые chat ID нормализуются; повторяющиеся адреса удаляются. Адрес ограничен 254 символами. Сервис существующего подключения неизменяем: для другого сервиса создаётся новая запись.

Telegram настраивается токеном и необязательным HTTP(S)-прокси. Email настраивается SMTP-сервером, портом, STARTTLS или SSL/TLS, логином и паролем, адресом и именем отправителя. SMTP без аутентификации возможен при пустом логине; защищённое соединение обязательно. Контактный email клиента используется только как `Reply-To`, адрес отправителя берётся из подключения. В email для каждого получателя создаётся отдельное письмо с текстовой и HTML-версией.

Раздел доступен активному суперпользователю; стандартных модельных прав сотрудника недостаточно. Подключение с историей доставок защищено от удаления через `PROTECT`; для остановки используется выключение. Штатный журнал Django Admin фиксирует изменения полей и запросы теста/повтора без значений секретов.

## Секреты

Токен, пароль SMTP и полный URL прокси хранятся в отдельных не редактируемых напрямую текстовых полях в формате Fernet. `forms.py` принимает новые значения в `PasswordInput(render_value=False)`, шифрует их перед модельной валидацией и никогда не подставляет сохранённые секреты в HTML. Пустое поле сохраняет старое значение; удаление прокси и SMTP-пароля выполняется отдельными флагами. Под флажком удаления SMTP-пароля поясняется ограничение: у включённого подключения с заполненным логином пароль обязателен, поэтому перед удалением нужно очистить логин или выключить подключение. Неуспешная форма также не возвращает введённый секрет.

`secrets.py` использует `cryptography` и `LEAD_DELIVERY_ENCRYPTION_KEYS` из окружения: список Fernet-ключей через запятую, первый для новых записей, остальные для чтения прежних значений. Ключи не выводятся в admin и не хранятся в базе или Git. При отсутствии/неверном формате ключа ввод нового секрета отклоняется; ранее настроенный Telegram из окружения продолжает работать. Потеря всех подходящих ключей требует повторного ввода секретов. Резервные копии ключей должны храниться отдельно от копий базы.

Для нового развёртывания создайте ключ командой в защищённом терминале:

```console
python -c "from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())"
```

Задайте полученное значение в `LEAD_DELIVERY_ENCRYPTION_KEYS` внутри закрытого `.env` либо окружения web-процесса и планировщика. После изменения окружения процессы должны получить новые настройки. При замене ключа оставляйте старый в списке, пока все секреты не сохранены заново под новым ключом; автоматической перешифровки существующих строк нет. Формат и ротация описаны в [документации Fernet](https://cryptography.io/en/latest/fernet/).

## Очередь и проверки

Публичные обработчики `pict` и `quiz` вызывают общий `enqueue_contact_request()` внутри транзакции сохранения заявки. Для каждого включённого подключения, подходящего по типу заявки, создаётся запись на каждого получателя. Нет активных подключений — заявка всё равно сохраняется. Сетевая отправка выполняется только командой `process_contact_deliveries`.

Адрес получателя копируется в доставку при постановке в очередь. Изменение списка получателей действует на новые доставки; накопленные продолжают использовать сохранённые адреса. Выключение прекращает постановку новых отправок и приостанавливает существующие, сохраняя их. Включение возобновляет очередь; заявки за период отключения автоматически не добавляются. Для них существует действие списка заявок «Отправить выбранные заявки в активные подключения». Оно создаёт только отсутствующие доставки по текущим правилам.

«Сохранить и отправить тест» сохраняет форму и создаёт в той же очереди группу сообщений без клиентских данных и без фиктивной заявки. Тест разрешён и для выключенного подключения. Внешнего вызова из admin POST нет. После следующего запуска команды и обновления страницы блок последней проверки показывает результат отдельно для каждого получателя. Группа определяется `test_batch_id`. Счётчик «В очереди» учитывает и тестовые доставки. Счётчик «Ошибок» и состояние «Есть ошибки отправки» учитывают только доставки реальных заявок; прежние неудачные тесты их не увеличивают. Карточка показывает только последнюю тестовую группу; старые тесты сохраняются в БД, но отдельного списка их результатов в admin нет. Ссылка «Открыть заявки» ведёт только к реальным заявкам, поэтому ошибочные тесты там не появляются.

Кнопка повтора в карточке подключения и действие в списке заявок возвращают только `retry`/`failed` обычных доставок в очередь с обнулением попыток. Отправленные и обрабатываемые записи не меняются. Для выключенного подключения повтор также ожидает включения. Подробности [обработчика](../pict/services.md) и [команды](../pict/management.md).

## Миграция и совместимость

`sitecontent/0004_leadconnection` создаёт таблицу и включённое подключение «Telegram (настройки сервера)». Оно использует прежние `TELEGRAM_BOT_TOKEN`, `TELEGRAM_PROXY_URL` и тайм-ауты. Пустой список получателей означает `TELEGRAM_CHAT_ID`; можно указать явный список, сохранив токен из окружения. Секреты из `.env` не копируются в базу.

`pict/0037_lead_deliveries` связывает старые доставки с подключением, сохраняет их статусы/попытки/даты/внешние ID, выдаёт каждой собственный UUID, заменяет уникальность «заявка + канал» на «заявка + подключение + получатель». Исторические строки не содержали адреса: он остаётся пустым и для ожидающей Telegram-доставки заполняется перед отправкой из прежнего TELEGRAM_CHAT_ID, а при его отсутствии — из единственного явно указанного Telegram-получателя. Это работает и после перехода с настроек окружения на секреты из admin. Если адрес определить нельзя, строка сохраняется без расхода попыток, а в карточке появляется пояснение; другие доставки с сохранёнными адресами продолжаются. Для исторической строки без адреса повторная постановка в то же подключение пропускается независимо от источника настроек, чтобы не дублировать прежнюю отправку. Старые email-записи, если они есть, относятся к выключенному подключению «Архив email».

Переход к нескольким получателям необратим обычной обратной миграцией: возврат требует согласованной резервной копии базы и прежнего кода. В локальной проверке миграция выполнена сначала на копии SQLite; исходные доставки сохранены. Менять команду планировщика не требуется.

## Файлы и проверки

- `sitecontent/models.py` — типизированные поля подключения, адреса, маршрутизация и валидация.
- `sitecontent/forms.py` — поля сервиса, выбор типов и безопасный ввод секретов.
- `sitecontent/secrets.py` — Fernet/MultiFernet.
- `sitecontent/admin.py` — доступ, состояние, постановка тестов и повторов.
- `sitecontent/templates/admin/sitecontent/leadconnection/change_form.html` — кнопки отправки теста и повтора.
- `sitecontent/static/sitecontent/js/lead-connection.js` — показ полей выбранного сервиса и синхронизация общего флажка с отдельными типами заявок.
- `sitecontent/test_lead_processing.py` — шифрование, смена ключа, формы, нормализация адресов, маршрутизация, отключение, SMTP и проверка его TLS-контекста, независимые ошибки, переход исторической очереди на настройки admin, защита захвата очереди, транзакции, права и CSRF. Тесты публичной формы используют подписанный токен возрастом 6 секунд, превышающий общий антиспам-порог 5 секунд.

Для текущих 10–20 одновременных посетителей используется существующая SQLite-очередь и ограниченная пачка отправок; отдельный постоянно работающий процесс и брокер очереди не добавлены. Успех означает принятие сообщения внешним сервисом, а не прочтение сотрудником или попадание письма во входящие. При неопределённом сетевом результате повтор может создать дубликат; стабильный email `Message-ID` помогает идентификации, но не гарантирует устранение дубликатов SMTP-сервером.
